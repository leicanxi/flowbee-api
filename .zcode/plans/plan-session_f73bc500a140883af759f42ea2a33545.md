# 邀请奖励改为余额返利（限首单 + 比例可配置 + 单笔封顶 + 手动扣回）

## 范围

**做**：邀请人奖励从固定积分改为「被邀请人首充到账额度 × 百分比」的余额返利；比例与单笔封顶可配置；每被邀请人仅首单返一次；提供管理员手动扣回兜底（不接任何支付渠道的退款 webhook——你只有易支付且基本不退款）。

**不做**：被邀请人的 `invitee_points` 积分奖励保持不变；不加 7 天资格窗口；不做延迟结算；不改 Stripe/Waffo 等 webhook；不动 `relaykit`/`tokenkit`。

## 1. 配置（沿用 WelfarePointsSetting JSON，管理端是 JSON 编辑器，无需新界面管道）

`setting/welfare_points.go` 的 `WelfarePointsSetting` 增加两个字段（加进 `CheckWelfarePointsSetting` 校验与 `copyWelfarePointsSetting`）：

- `inviter_rebate_percent`（float，0–100，0=关闭返利、维持现有积分行为）
- `inviter_rebate_max_quota`（int，单笔返利封顶，quota 单位；0=不封顶）

新增 getter `GetWelfareInviterRebatePercent` / `GetWelfareInviterRebateMaxQuota`：**不**跟随 `Enabled` 开关（返利是钱，与福利积分经济解耦），只看字段本身。合规门槛维持现状：发放时用 `operation_setting.IsPaymentComplianceConfirmed()` 门控（与现积分奖励一致），不在保存时额外拦截。

管理端模板字符串补上新键：`web/src/features/system-settings/general/welfare-points-section.tsx` 的 `DISABLED_DEFAULT`/`EXAMPLE`、`web/src/features/system-settings/billing/index.tsx` 的重置默认 JSON。

## 2. 发放逻辑（`model/topup.go` 的 `creditInviterReward` 重做，六个支付入账调用点不动事务结构）

新流水表 `invite_rebate_logs`（GORM AutoMigrate 注册进 `model/main.go`）：

```
Id, TopupId(唯一索引), InviterId(索引), InviteeId, Amount(int, 实发quota), Status("granted"/"clawed_back"), CreatedAt, ClawedAt
```

发放流程（充值入账事务内）：
1. 复用现有首充判定（topup.go:152-161，排除当前订单的成功充值计数）与合规门控；`topup_id` 唯一索引幂等。
2. `percent > 0` 时：`rebate = common.QuotaFromDecimal(creditedQuota × percent/100)`（decimal 计算，禁止裸 cast），超封顶取 `min(rebate, max_quota)`；结果 ≤0 不发。
3. 给邀请人入账复用 `creditTopUpQuota(tx, inviterId, rebate, nil)` 的条件 UPDATE 封顶语义；邀请人钱包已满封顶时记 `SysError` 后跳过返利，**不影响被邀请人充值入账**。
4. 幂等顺序：先查流水 → 信用入账 → 插流水行（唯一索引兜底并发）。
5. `percent == 0` 走现有 `inviter_points` 积分路径，行为完全不变；`invitee_points` 积分照旧发放。

日志：`creditInviterReward` 返回值从 `(inviterId, reward int, err)` 改为 `(inviterId int, msg *common.Message, err error)`，六个调用点改为 `if msg != nil { RecordLog(...) }`。返利文案新 key「Invited user's first top-up awarded {{amount}} balance rebate」；积分路径沿用旧 key。

## 3. 手动扣回（兜底，仅管理员）

- `model` 层 `ClawbackInviteRebate(tradeNo)`：事务内行锁流水行，`granted` → 标记 `clawed_back`，并从邀请人余额扣回 `Amount`，**扣到 0 为止不产生负余额**（可移植的 `CASE WHEN quota >= ? THEN quota - ? ELSE 0 END`，三库通用）；已扣回则幂等返回。
- 路由：`adminRoute.POST("/topup/rebate_clawback", ...)`（与现有 `/topup/complete` 并列），入参 trade_no。
- 给被扣回人写 `RecordLog`，新 key「Invite rebate of {{amount}} was clawed back」。

## 4. 展示与统计

- `controller/user.go` `buildSelfUserData` 的 `aff_issued_count`：改为「积分流水 source=inviter 条数 + 返利流水 granted 条数」。
- `controller/welfare_points.go` `GetWelfarePoints` 响应加 `inviter_rebate_percent` / `inviter_rebate_max_quota`；`web/src/features/dashboard/api.ts` 的 `WelfarePointsConfig` 类型同步。
- 钱包页 `web/src/features/wallet/components/affiliate-rewards-card.tsx` 规则文案：返利开启时显示「首充到账额度 {{percent}}% 余额返利（单笔最高 {{cap}}）」的新句子（cap=0 时用不带封顶的变体 key），关闭时维持原文案。

## 5. i18n（用 i18n-translate 技能执行）

新增/改动 key 全部进 7 个 locale（en/zh/zh-TW/fr/ru/ja/vi）：后端两条消息 key + 钱包规则句子（1–2 个变体）。旧 key 保留（积分路径仍在用）。

## 6. 测试（集中一个新文件 + 扩一个前端测试）

**`model/topup_invite_rebate_test.go`（唯一新后端测试文件）**，沿用 `model/task_cas_test.go` 的 SQLite 内存夹具与 `payment_method_guard_test.go` 的 RechargeEpay 模式，testify require/assert：
1. 首充按比例返余额（quota 增量 = 到账额度 × 5% 截断取整）、被邀请人照常得积分；
2. 重复回调幂等不双发；
3. 第二笔充值不返；
4. 单笔封顶生效；

7. 邀请人钱包触顶时返利跳过且充值仍成功。
